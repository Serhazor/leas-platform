# Architecture

## Principles

- **French everywhere users look** (public site, admin, e-mails, errors); English for code and docs.
- **Content lives in the database**, never in React components. `src/db/seed-data.ts` only
  provides the initial copy; `src/lib/content/registry.ts` only describes *which fields* each
  page section offers and how they are labelled in the admin.
- **Serverless-friendly**: no long-running process. Everything runs as Vercel functions,
  static/ISR pages and one daily cron.
- **Small surface**: no CMS framework, no auth provider, no analytics, no cookie banner needed.

## Data model (PostgreSQL, `src/db/schema.ts`)

| Table | Purpose |
| --- | --- |
| `admin_users`, `admin_sessions`, `password_reset_tokens`, `login_attempts` | Authentication |
| `site_settings` (single row) | Identity, contact, branding, SEO defaults, booking rules, e-mail, legal info |
| `pages`, `page_sections` | Editable pages; sections have typed fields (eyebrow, heading, body, image, 2 CTAs, repeatable `items`) |
| `service_categories`, `services`, `service_images` | Services, ordering, pricing, booking options, SEO, gallery |
| `process_steps`, `faqs` | "Comment ça marche" steps, FAQ (ordering, visibility, home display) |
| `media` | Media library (storage key, public URL, dimensions, ALT text) |
| `availability_rules` | Weekly hours (several ranges per weekday) |
| `blocked_periods` | Holidays, days off, blocked dates or time ranges |
| `bookings` | Appointments; machine status codes `pending/confirmed/refused/cancelled/completed` (French labels in `lib/booking/status.ts`) |
| `contact_enquiries` | Contact form messages (`new/in_progress/done`) + internal notes |
| `activity_log` | Dashboard "Activité récente" and per-booking history |

All tables have `created_at` / `updated_at` (timestamptz). Migrations live in `/drizzle`
(generated by drizzle-kit from the schema + one custom migration).

**Database guarantees** (`drizzle/0001_security_and_constraints.sql`):
- `bookings_no_overlap`: GiST exclusion constraint — two *pending/confirmed* bookings can never overlap.
- Row Level Security enabled on every table with no policy + privileges revoked from Supabase's
  `anon` / `authenticated` roles → the Supabase Data API exposes nothing.

## Authentication

Custom, database-backed sessions (`src/lib/auth`):
- scrypt password hashes (Node built-in, no native dependency);
- 32-byte random session token in an `httpOnly`, `SameSite=Lax`, `Secure` cookie; only its
  SHA-256 hash is stored; 14-day expiry; sessions revoked on password change;
- login throttling (5 failures / 15 min per e-mail, 20 per hashed IP), constant-time response
  for unknown e-mails; password reset by e-mail (1-hour single-use token);
- **no registration**: accounts are created with `npm run admin:create` or by an admin in
  *Paramètres → Accès*.
- `src/proxy.ts` (Next.js 16 proxy) redirects cookie-less requests; **every admin page and
  server action calls `requireAdmin()`**, which validates the session in the database.
  Server Actions also benefit from Next.js' built-in Origin check (CSRF).

Why not Supabase Auth? A single-owner back-office needs no OAuth/MFA flows, and a custom
implementation keeps every screen and e-mail in French with no extra service to configure.
Supabase Auth could be introduced later for customer accounts.

## Booking engine (`src/lib/booking`)

- `slots.ts` — **pure** functions (unit-tested): weekly rules × closures × existing bookings ×
  buffer × minimum notice × maximum advance × per-service duration × slot interval, computed in
  the business time zone (`Europe/Paris`, DST-safe via `Intl`), stored in UTC.
- `engine.ts` — loads data and creates bookings in a transaction guarded by
  `pg_advisory_xact_lock(date)`; availability is recomputed inside the transaction and the
  exclusion constraint is the final safety net (error → "Ce créneau n'est plus disponible").
- Two modes (*Paramètres → Réservations*): **request** (status `pending`, the slot is held until
  the owner confirms/refuses) and **instant** (status `confirmed`).
- `GET /api/disponibilites?service=…&mois=YYYY-MM | &date=YYYY-MM-DD` feeds the calendar (no cache).
- E-mails and activity logging run in `after()` so the visitor is not kept waiting.

**Google Calendar later**: implement `CalendarProvider` (`src/lib/calendar/provider.ts`) —
`getBusyIntervals()` is already merged into slot computation and `onBookingChanged()` is already
called on creation and every status change; `bookings.external_calendar_event_id` is reserved.

## Content management

`registry.ts` declares, per page, the sections and fields shown in the admin with business
labels ("Bandeau principal", "Bouton principal", "Texte"…). The owner never sees JSON: repeated
items are edited with add / move / delete buttons; links are chosen from a list of site pages.
Body text supports a tiny, safe format (blank line = paragraph, "- " = list, "## " = sub-heading,
URLs auto-linked) rendered by `components/ui/RichText.tsx` — no HTML is ever interpreted.

UX safeguards: sticky save bar, "Modifications non enregistrées" indicator, leave-page
warning, confirmation dialogs for destructive actions, French validation messages, toasts,
raw errors never shown (logged server-side instead).

## Media

1. The browser resizes (max 2400 px) and converts to WebP (`components/admin/useMediaUpload.ts`).
2. A server action returns a one-time **signed upload URL**; the file goes straight to Supabase
   Storage (bypasses Vercel's 4.5 MB request limit).
3. The file is registered in `media` (dimensions, ALT text). "Remplacer" swaps the file while
   keeping every reference; deletion shows where the image is used.
4. Delivery uses `next/image` (AVIF/WebP, responsive sizes, lazy loading, 31-day cache).

`lib/storage` is an interface (`StorageDriver`): Supabase (production), local disk
(development), and photos committed in `public/images` (registered by the seed with a
`static/` key, never deleted). **Cloudinary** can be added by implementing the same four
methods (direct upload URL, public URL, exists, remove) and selecting it in `getStorage()`.

## Rendering, caching & performance

- Public pages are static/ISR (`revalidate = 3600`); every admin mutation calls
  `revalidatePath("/", "layout")` so changes are visible immediately.
- Service pages are prerendered via `generateStaticParams`, new ones rendered on demand.
- Client JavaScript is limited to: mobile menu, active nav link, contact form, booking wizard.
  FAQ accordions use native `<details>`.
- Fonts are self-hosted (`@fontsource-variable` + `next/font/local`): no Google request,
  no layout shift. Three font pairings selectable in the admin.
- Vercel region `cdg1` (Paris) next to a Supabase Paris database.

## Theme system

`site_settings` stores primary/secondary/accent colours and a font pairing. `lib/theme.ts`
turns them into CSS custom properties on `<html>` (with automatic readable text colour and
a contrast warning in the admin). Tailwind tokens (`bg-primary`, `text-accent`, `font-serif`…)
read those variables, so rebranding needs no code change. Logo and favicon come from the
media library (fallback: company name in the display font, `public/favicon.svg`).

## SEO & accessibility

Per-page editable title/description/share image, global defaults, canonical URLs, Open Graph &
Twitter cards, `lang="fr"` / `fr_FR`, `sitemap.xml`, `robots.txt` (admin/API excluded, previews
not indexed), JSON-LD: `ProfessionalService`, `Service`, `FAQPage`, `BreadcrumbList`.
Semantic landmarks, skip links, labelled form controls with `aria-invalid`/`aria-describedby`,
visible focus rings, keyboard-navigable date picker and time slots, reduced-motion support.

## RGPD

- Data minimisation: only the fields needed for the request; explicit consent checkbox with
  timestamp; privacy policy lists processors (Vercel, Supabase, Resend) and retention.
- No analytics, trackers or third-party fonts; the public site sets **no cookies** (hence no
  banner). The admin session cookie is strictly necessary.
- Daily retention job (`/api/cron/nettoyage`); IPs are only stored hashed (login throttling).
- Security headers: CSP, HSTS, `X-Frame-Options: DENY`, `nosniff`, strict referrer, permissions policy.
- If consent-requiring analytics are added later, add a consent manager **before** loading them.

## Future evolution (not implemented, not blocked)

- **Customer / business / staff accounts**: add tables referencing `bookings` (a nullable
  `customer_id`); the admin auth module can host roles (`admin_role` enum already exists).
- **Properties, rooms, inspection records, photos per item, e-signatures, PDF reports,
  move-in/move-out comparison**: new domain tables linked to `bookings` and `media`;
  the booking flow and media pipeline are reusable as-is.
- **Invoicing / online payments**: attach to `bookings`; Stripe webhooks fit Vercel functions.
- **Multilingual**: `pages`/`page_sections` can gain a `locale` column; routes can move under
  `[locale]` segments.
- **Event services**: already modelled as a category with "Bientôt disponible" services.
